# Codex 严格审查协议

## 1. 目的

本协议用于约束 Codex 在每一轮审查时的最低动作与最低标准，避免把“测试通过”误当作“数学正确”或“命令已完整复现”。

## 2. 审查总原则

### 2.1 数学实现优先于数值拟合

审查的第一问题不是“结果是否接近”，而是：

- 实现过程是否与 Stata 手册或源码对应
- 数学对象是否一致
- 推断口径是否一致

如果代码只是为了通过样例在数值上靠近 Stata，而无法说明其数学来源，则视为不通过。

### 2.2 源码优先于样例

对 `research/vendor/stata_community/` 下的命令，审查时必须优先核对：

- Python 行为能否指出对应 `.ado` / `.mata` 路径
- 关键公式、修正因子、边界处理是否有源码依据

### 2.3 测试通过不是充分条件

即使 synthetic、real-data 和全量 `pytest` 都通过，仍然必须单独判断：

- 是否存在宽容差掩盖
- 是否存在静默忽略参数
- 是否存在错误但未覆盖的公开 API 语义

## 3. 每轮审查前的固定动作

每轮开始审查前，Codex 至少执行：

1. 读取当前任务卡
2. 读取当前 `REPORT.md`
3. 抽查被修改的研究文档、支持矩阵、核心实现文件
4. fresh run 当前任务涉及的专项测试
5. fresh run 全量测试

不得只根据 Claude Code 的报告文本做判断。

## 4. 数学审查清单

对任何估计器或命令，至少逐项检查：

- 目标对象
- 样本与设计矩阵
- 估计过程
- 推断过程
- 公开语义

具体看：

- 样本剔除顺序
- 权重处理
- FE / absorb / dummies 构造
- singleton / omitted / collinearity 处理
- OLS / within / 2SLS / MLE / IRLS / DID aggregation 的数学过程
- `t` vs `z`
- `F` vs `Wald chi2`
- cluster / robust sandwich score
- wrapper 名称、参数映射、错误处理

## 5. 反“凑数值”检查

审查时必须特别寻找以下迹象：

- 容差异常宽
- 只对单一样例通过
- 针对单一 real-data case 写的特殊修补
- 公式里出现无法解释的系数
- 参数被读取但没有实际生效
- 报告把“尚未解释的差异”写成“可接受”

只要发现上述任一迹象，就不能直接通过。

## 6. 测试审查要求

Codex 在审查时可以并且应当增加额外核验，例如：

- 直接构造小样本矩阵检查公式
- 单独核对 `reported_p` 是否真等于 z-based / t-based 值
- 对 wrapper 做非法参数 spot check
- 检查 `_cons`、offset、weights 等容易漏掉的公开语义

## 7. 必须打回的情形

出现以下任一项，必须打回：

- 推断分布口径错误
- sandwich / score / df 修正逻辑错误
- 宽容差掩盖系统偏差
- wrapper 静默忽略参数
- 报告夸大完成度
- 支持矩阵与真实实现不一致
- 无法说明源码/手册依据

## 8. 当前下一轮的特别审查重点

### 8.1 `compat.stata` 命令层

- 是否真的存在
- 是否具备命令语义
- 参数是否正确映射

### 8.2 `reghdfe` / `ivreghdfe` / `ppmlhdfe`

- 是否引用了本地源码镜像中的真实逻辑
- 是否只是在已有最小实现上换了个名字

### 8.3 支持矩阵

- 是否诚实
- 是否把未支持功能错误地写成已支持

## 9. 审查输出要求

如果不通过：

- 必须生成正式 review 文档
- 必须指出具体阻塞点
- 必须说明是数学错误、语义错误、证据链错误还是状态管理错误

如果通过：

- 必须说明 fresh verification 结果
- 必须说明为什么它不仅测试通过，而且数学逻辑也站得住
- 才能签发下一张任务卡
